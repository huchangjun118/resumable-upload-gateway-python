# 架构与一致性语义

本文描述面向大文件的本地对象上传/存储网关的内部状态机、并发与崩溃一致性
保证。所有处理只使用本地磁盘与进程内同步，不依赖任何外部对象存储或网络服务。

## 1. 磁盘布局

所有状态位于 `Config.data_dir` 下：

```
data/
├── sessions/<tenant>/<session_id>/
│   ├── meta.json              # 会话元数据（原子写）
│   ├── journal                # 提交意图（仅 COMMITTING 期间存在）
│   └── chunks/00000000 ...    # 已确认分片（每个独立文件）
├── objects/<tenant>/
│   ├── <object-name...>       # 已提交、对外可见的对象
│   └── .staging/<sid>.tmp     # 提交时拼装的暂存文件
└── quota/<tenant>.json        # 每租户配额台账
```

关键规则：

* `meta.json`、`journal`、`quota/*.json` 都通过“临时文件 + `fsync` +
  `os.replace` + 父目录 `fsync`”落盘，单次写入要么完整可见要么不存在。
* 分片先写到 `NNNN.recv.<pid>` 临时文件，**完整读入、大小与 SHA-256 全部
  校验通过后**才 `os.replace` 为正式分片；失败只删临时文件，绝不触碰已确认
  分片。
* 对象对外可见通过**一次** `os.replace(staging, target)` 完成。POSIX 的
  rename 是原子的，且暂存文件已 `fsync`，因此读方要么看到旧版本要么看到
  新版本，永远不会读到半个文件或混合版本。

## 2. 会话状态机

```
                 create_session
                       │
                       ▼
              ┌──────────────┐   第一个分片确认
              │     INIT     │──────────────┐
              └──────────────┘              ▼
                    │                ┌──────────────┐
                    │                │ IN_PROGRESS  │◀────┐ 提交失败回滚
                    │                └──────────────┘     │（分片保留，可重试）
                    │     put_chunk(乱序/重复/迟到)        │
                    ▼                    │ commit        │
              ┌──────────────┐          ▼                │
              │  COMMITTING  │  校验+拼装+rename          │
              └──────────────┘──────────────┐            │
                    │                        ▼            │
             成功   │               ┌──────────────┐     │
             ───────┼──────────────▶│  COMPLETED   │     │
                    │               └──────────────┘     │
        abort / 过期 │                                   │
                    ▼                                    │
        ┌──────────────┐   ┌──────────────┐             │
        │  CANCELED    │   │   EXPIRED    │             │
        └──────────────┘   └──────────────┘─────────────┘
```

状态语义：

| 状态 | 含义 | 是否接受分片 | 是否可见对象 |
|------|------|:---:|:---:|
| `init` | 已建会话，尚未确认任何分片 | 是 | 否 |
| `in_progress` | 至少一个分片确认 | 是 | 否（提交前完全不可见） |
| `committing` | 提交进行中 | 否（明确拒绝） | 读旧版本 |
| `completed` | 对象已原子发布 | 否 | 是 |
| `canceled` | 客户端取消 / 提交失败出局 | 否 | 否（无残留） |
| `expired` | 超过保留期被回收 | 否 | 否（无残留） |

* **继续上传**：客户端记录 `session_id`，中断后用 `GET` 查询缺失分片
  （`missing_chunks`），补传即可。分片在全部确认前只是私有文件，对象完全
  不可见。
* **重复创建**：
  * 带相同 `idempotency_key` 的创建是幂等的，返回同一个会话；若同 key 但
    `object_name/total_size` 不同，返回确定性 `400` 冲突。
  * 显式指定已存在的 `session_id` 返回 `400`，不产生重复。
* **迟到请求**：对 `committing/completed/canceled/expired` 的分片写入均以
  明确的错误码拒绝（`session_closed/session_completed/session_canceled/
  session_expired`），绝不静默丢弃。

## 3. 分片语义

* 分片偏移由 `number * chunk_size` 服务端推导，末片大小为
  `total_size - offset`，不接受越界分片。
* 每个分片必须带 64 位十六进制 SHA-256（`X-Content-Sha256`）。
* **乱序**：按编号独立确认，提交时按编号顺序拼装。
* **重复**：
  * 已确认编号 + 相同摘要 → 幂等成功，且会重新校验重传字节；
  * 已确认编号 + 不同摘要 → 拒绝，已确认数据不可变。
* **缺失/损坏**：缺失在提交时以 `missing_chunks` 明确报出编号列表；大小或
  摘要不符立即 `400` 拒绝，且不留临时文件、不写入元数据。
* 可选 `whole_sha256` 在拼装阶段对整体对象再校验一次。

## 4. 并发与覆盖策略

* 每个对象名有一把**提交锁**，且在把会话翻成 `committing` 之前持有，因此
  同一对象的“裁决 → 拼装 → 发布”严格串行；不同对象互不阻塞。
* 每个会话创建时获得单调递增的 `create_seq`。

### `overwrite_policy = "always"`（默认）

同一对象名存在多个未结束会话时，**最后创建的会话（最大 `create_seq`）
胜出**，结果与调度顺序无关。较早的会话在自己的提交回合得到确定性
`409 object_already_exists`，其分片、暂存文件、元数据与配额预留被立即、
完整清理，不留任何可见残留。

除了比较内存中的活动会话，服务还为每个对象维护“已发布版本胜出水位”
（winner 的 `create_seq`）：任何 `create_seq` 不大于已发布版本的会话在
裁决时一律判负，即使胜出会话已从内存索引移除（例如陈旧的 `committing`
会话或崩溃残留），也不可能覆盖更新的对象。该水位在启动恢复时以
`self._seq` 为现存对象重新播种，而新会话的序号必然更大，因此正常的后续
覆盖不受影响。

### `overwrite_policy = "never"`

对象已存在即拒绝覆盖，提交会话被确定性取消并清理，旧对象保持不动。

### 提交期间到达的请求

| 请求 | 行为 |
|------|------|
| 读对象 `GET/HEAD` | 返回**当前已发布版本**（rename 前旧版，rename 后新版），永不阻塞或读到半成品 |
| 写分片 `PUT chunk` | `409 session_closed`（会话正在提交） |
| 竞争会话提交 | 在对象锁后串行裁决，恰一个胜出，其余 `409` 并清理 |

已打开的读文件句柄始终对应某一个完整版本（rename 不影响已打开 inode）。

## 5. 归属与配额

* 租户由 `X-Tenant-Id` 标识（参考信任模型，生产应在网关接入真实鉴权）。
* 用量 = 已提交对象字节数 + 未结束会话的**预留**字节数。
* 创建会话时**先**检查并预留 `total_size`，超额在创建任何目录/元数据之前
  抛 `413 quota_exceeded`，因此拒绝不会留下孤儿分片或元数据。
* 提交成功时预留转为已提交；覆盖时自动回收被替换版本的字节数；
  取消/过期/提交出局时释放整笔预留。
* 配额台账持久化；启动时以磁盘真实状态**重建**，崩溃不会泄漏或重复占用。
* 可配置每租户并发会话上限 `max_sessions_per_tenant`。

## 6. 崩溃恢复

启动（`start()`/`recover()`）时：

1. 扫描 `sessions/` 载入全部会话与最大 `create_seq`。
2. 对停留在 `committing` 的会话，依据 `journal` 与磁盘状态对账：
   * 目标对象已存在且大小正确（rename 已发生）→ 完成记账、删除日志与会话；
   * 否则从已确认分片重新流式拼装、整体校验、原子 rename 后完成；
   * 拼装/校验失败 → 回滚为 `in_progress`，分片保留，客户端可重试提交。
3. 最后以“对象目录实际字节 + 未结束会话预留”**权威重建**每租户配额，覆盖
   崩溃前的中间记账。

因此：已确认分片与已提交对象在重启后保持一致且可继续；对象可见性仍由
rename 保证，不会因重启产生半成品。

## 7. 保留与回收

* 会话有 `expires_at = 最近活动时间 + session_ttl_seconds`，每次分片确认/
  提交回滚都会滑动续期。
* 后台回收线程（`reap_interval_seconds`，设 0 关闭）与手动
  `reap_expired()` 只会取消已过期且**未结束**的会话：删除分片/元数据、
  释放预留。
* `committing` 与 `completed` 不受回收影响。

## 8. 流式处理与有界内存

* 分片请求体经单槽有界缓冲从事件循环交给工作线程，背压天然存在，最多缓存
  约一个 `read_buffer_size`。
* 落盘、提交拼装、对象读取全部以固定大小缓冲流式进行，额外内存不随对象
  大小增长。
* 阻塞式文件 IO 在线程池（`anyio.to_thread`）执行，事件循环不被大文件
  传输阻塞；不同对象的提交使用各自的锁，互不拖垮吞吐。
